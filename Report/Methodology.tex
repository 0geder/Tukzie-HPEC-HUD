\chapter{Design}
\label{chap:design}

Chapter~\ref{chap:method} set out the approach: a V-model in which each design stage has a matching test, run in six phases. This chapter is the design and implementation of phase 3, the system as built on 21 October 2026, on which the experiments of Section~\ref{sec:experiments} were run. It is structured as follows. Section~\ref{sec:architecture} gives the system-level design and the choice of architecture. Section~\ref{sec:hardware} covers the hardware. The software follows: the telemetry unit's firmware (Section~\ref{sec:dual-imu-architecture}), its ride-characterisation processing (Section~\ref{sec:ride-characterisation}), the battery-management interface (Section~\ref{sec:bms-interface}), positioning (Section~\ref{sec:gnss-parsing-validation}), the other vehicle inputs (Section~\ref{sec:environmental-sensing}) and the camera subsystem (Section~\ref{sec:camera-subsystem}). The integration design is in the dashboard integration (Section~\ref{sec:dashboard-page}), the two-sided layout (Section~\ref{sec:two-sided}) and the communications and logging (Section~\ref{sec:mqtt-networking}). Section~\ref{sec:investigations} gives the fault investigations that shaped the design, Section~\ref{sec:bench-tools} the testing infrastructure and Section~\ref{sec:maintenance} the maintenance design. Each major section opens by naming the requirements of Table~\ref{tab:requirements-mapping} and the research questions it serves, so that the chain from objectives to requirements, design, tests and conclusions can be followed.

Development followed a staged approach: each interface was tested on its own before higher-level functions were added, so that a fault could be traced to one change. The seven faults whose diagnosis shaped the design are worked through in Section~\ref{sec:investigations}; the full development record, with every fault, its cause and its fix, is in Appendix~\ref{app:devrecord}, and the firmware configuration (versions, pins, bus speeds, task priorities, queue depths and partitions) is in Table~\ref{tab:config} of that appendix.

\section{System overview and architecture selection}
\label{sec:architecture}

This section serves all thirteen requirements at system level, R1 and R7 in particular, and through them RQ1 to RQ4. Figure~\ref{fig:system-architecture} shows the system. An ESP32-S3 telemetry unit samples two inertial measurement units (IMUs), reads GNSS and the battery-management system (BMS), computes ride features, logs locally and publishes over LTE. Two camera units each run the detector and fuse it with three time-of-flight sensors: the vehicle's existing dashboard computer, a Raspberry Pi~5 beside the display, faces forward, and a Raspberry Pi~4 beside the battery faces backward and also bridges the telemetry unit's data. The two are joined by an Ethernet cable (Section~\ref{sec:two-sided}). In the first bench versions the Raspberry Pi~4 faced forward and the dashboard read it over Wi-Fi.

\section{Hardware}
\label{sec:hardware}
\label{sec:camera-mount}

This section serves R1, R4, R5, R6, R8 and R13, and RQ1 and RQ3. The telemetry unit is a Makerfabs ESP32-S3 4G LTE CAT1 A7670X board: an ESP32-S3-WROOM-1-N16R8 module (16\,MB flash, 8\,MB PSRAM) with an A7670X LTE Cat-1 modem that also contains the GNSS receiver \cite{makerfabsa7670x} (Figure~\ref{fig:makerfabs-pinout}, Appendix~\ref{app:figures}). The integrated board lets processor, modem and GNSS be tested without a separate modem circuit. Two MPU6050 IMUs are on separate I\textsuperscript{2}C buses at 400\,kHz, which avoids their shared address and bus contention. The modem is on a hardware UART at 115200\,bit/s, with its power key and reset on GPIO~4 and~5. The board's microSD slot was not used: its chip-select line passes through a resistor (R23) that the schematic marks as not fitted, so local logging uses the internal flash (Section~\ref{sec:local-logging}).

Each camera unit carries an OV5647 camera module without an infrared-cut filter and three VL53L0X time-of-flight sensors on its I\textsuperscript{2}C bus: the Raspberry Pi~5 beside the display faces forward, and the Raspberry Pi~4 beside the battery faces backward and also takes the sync-pulse input on GPIO17 (Section~\ref{sec:two-sided}). The Raspberry Pi~4's camera is on a 15\,cm ribbon. Each camera is housed in a three-part casing designed and 3D printed in this project (Figure~\ref{fig:camera-casing}, Appendix~\ref{app:figures}), not yet fixed to the vehicle. The enclosures and mounts designed to put the system on the vehicle (the dashboard display mount, the two sensor pods and the IMU pods), the choices behind them and the checks on their geometry are in Appendix~\ref{app:mechanical}; none had been printed by 12 October. Every connection is listed in Appendix~\ref{app:wiring}, and Figure~\ref{fig:bench-setup} shows the bench setup.

\section{Firmware architecture}
\label{sec:dual-imu-architecture}
\label{sec:acquisition-instrumentation}

This section serves R1 and R6, and RQ1 and RQ3. The firmware is written with PlatformIO and the Arduino framework on FreeRTOS (Table~\ref{tab:config}). Figure~\ref{fig:task-architecture} shows its tasks and queues. The two IMU tasks run at the highest priority on core~1, each holding a 5\,ms period with \texttt{vTaskDelayUntil}, which schedules each wake-up from the previous target time so that variable execution time does not accumulate into drift. After a stall longer than a period it returns at once for each missed period, so the missed samples are read in a burst about 1\,ms apart: none is lost, but they are unevenly spaced. The modem, BMS and dashboard-line tasks run on core~0, away from acquisition.

\begin{figure}[htbp]
\centering
\input{figures/tikz/firmware_tasks}
\caption{FreeRTOS tasks and queues (drawn for firmware v0.7.1; unchanged in v0.7.3 and v0.7.4). Priorities as set in the firmware (higher runs first); each queue is labelled with its name and capacity in items. Queues between the two cores are drawn in blue.}
\label{fig:task-architecture}
\end{figure}

The 200\,Hz rate was chosen from the 80\,Hz upper limit of the ISO~2631-1 whole-body band \cite{iso2631}: sampling that band needs more than 160\,Hz, its Nyquist rate, and 200\,Hz adds margin without loading the bus heavily. The standard is used only for the band; its frequency weighting is not applied (Section~\ref{sec:ride-characterisation}). Each sample carries a sensor identifier, a per-sensor sequence number and a timestamp from \texttt{esp\_timer\_get\_time()}, a monotonic microsecond clock unaffected by network time. No acquisition task prints, because serial output blocks for a variable time and would disturb the period being measured. When a queue is full the producer drops the new sample and counts it rather than blocking, so a slow consumer can never hold up sampling. Each IMU feeds two queues, one to the statistics task and one to its ride-characterisation task, so that adding processing cannot change the acquisition accounting.

A lower-priority statistics task drains the queues and reports, every 2\,s and per sensor, the achieved rate, the minimum, mean and maximum interval between samples and the drop count, with the GNSS poll and fix counts. These counters produce the acquisition results of Chapter~\ref{chap:results} without a separate measurement pass, on the bench or on the vehicle.

Each IMU is set to $\pm 8\,g$ and $\pm 500^{\circ}$/s. Up to v0.7.3 the digital low-pass filter was at 260\,Hz, which lets vibration between the 100\,Hz Nyquist frequency and 260\,Hz alias into the band; v0.7.4, flashed on 11 October, uses 94\,Hz, the widest setting below the Nyquist frequency. Bench results before 11 October used 260\,Hz; test T15 and the road test use 94\,Hz. The $\pm 8\,g$ range gives headroom for pothole and kerb impacts while keeping resolution; it is provisional, to be set from the peaks the vehicle produces, and samples at the limit are not flagged, so a clipped window under-reports its peaks.

\section{Ride-characterisation signal processing}
\label{sec:ride-characterisation}

This section serves R2 and R3, and RQ1 and RQ4. A task per IMU computes time-domain features from each one-second window. Features use the acceleration magnitude rather than one axis because the mounting has not been related to a vehicle frame; the magnitude does not depend on orientation, at the cost of not saying which axis a disturbance came from. Each window holds $N = 200$ samples ($f_s = 200$\,Hz, $\Delta t = 1/f_s$). The calibrated magnitude of sample $k$ is
\begin{equation}
a_k = s\,\sqrt{a_{x,k}^2 + a_{y,k}^2 + a_{z,k}^2},
\label{eq:magnitude}
\end{equation}
where $s$ is the sensor's calibration factor. From the window,
\begin{align}
\mu &= \frac{1}{N}\sum_{k=1}^{N} a_k, &
a_{\mathrm{RMS}} &= \sqrt{\frac{1}{N}\sum_{k=1}^{N} a_k^2}, &
\sigma &= \sqrt{\frac{1}{N}\sum_{k=1}^{N} a_k^2 - \mu^2}, \label{eq:mean-rms-std}\\
a_{\mathrm{pp}} &= \max_k a_k - \min_k a_k, &
\mathrm{CF} &= \frac{\max_k a_k}{a_{\mathrm{RMS}}}, &
\bar{J} &= \frac{1}{N-1}\sum_{k=2}^{N} \frac{\lvert a_k - a_{k-1}\rvert}{\Delta t}, \label{eq:pp-cf-jerk}
\end{align}
and the threshold count is the number of samples with $a_k > \mu + 2\sigma$. Because $a_k$ includes gravity, $a_{\mathrm{RMS}}$ is close to 9.8\,m/s\textsuperscript{2} at rest and the crest factor close to 1; $\sigma$ removes the constant part and is the vibration measure used. Lost samples are counted, not interpolated, and $\Delta t$ is the nominal period, not the measured interval, so the jerk of a window that contains an acquisition pause is distorted. The ISO~2631-1 frequency weighting is not implemented, so the features describe vibration exposure, not comfort as the standard defines it. At every boot the feature code is checked against a synthetic 5\,Hz sine of 200 samples, whose RMS, peak-to-peak and crest factor have closed-form values ($A/\sqrt{2}$, $2A$, $\sqrt{2}$), with a tolerance of 5\%.

\subsection{Per-sensor calibration}
\label{sec:imu-magnitude-calibration}

Two nominally identical sensors at rest on the same platform read 10.35 to 10.39 and 9.55 to 9.56\,m/s\textsuperscript{2}, about 5.7\% above and 2.6\% below standard gravity, a disagreement of about 8\%. Since only the magnitude is used, one scale factor per sensor corrects it: RMS, $\sigma$, peak-to-peak and jerk scale linearly with it, and crest factor and the threshold count are unaffected. The first time a sensor is found with no stored factor, the firmware averages 200 stationary readings and stores
\begin{equation}
s = \frac{g_0}{\frac{1}{200}\sum_{k=1}^{200} \sqrt{a_{x,k}^2 + a_{y,k}^2 + a_{z,k}^2}}, \qquad g_0 = 9.80665\,\mathrm{m/s^2},
\label{eq:calibration}
\end{equation}
in non-volatile storage, rejecting values outside 0.5 to 2.0 as evidence that the sensor was moving. The factor is reused at every boot rather than recomputed, since the vehicle may be powered while moving, and a console command erases it so the sensors can be recalibrated in their mounted position (not yet used). A single factor corrects the reading only in the orientation in which it was measured, because per-axis offsets remain; this is why the factors changed between boards (Chapter~\ref{chap:results}).

\subsection{Speed-normalised index}
\label{sec:speed-norm}

The same road driven faster gives a larger response. Following Li et al., who classify roughness from acceleration mean square divided by speed \cite{li2018}, each window also computes
\begin{equation}
I_v = \frac{\sigma^2}{v}, \qquad v \ge v_{\min},
\label{eq:speed-index}
\end{equation}
where $v$ is the latest GNSS speed and $v_{\min} = 1$ in the receiver's units, so that $I_v$ is in (m/s\textsuperscript{2})\textsuperscript{2} per unit of that speed; without a fix or below $v_{\min}$, $I_v$ is not computed. Firmware before v0.7.2 used $a_{\mathrm{RMS}}^2$, which is dominated by gravity; v0.7.2 uses the variance. Two limits apply: the manual gives the speed in knots, but the unit's readings have not yet been checked against a known speed (Section~\ref{sec:gnss-parsing-validation}), so $I_v$ supports relative comparison within one dataset only; and the sensors are on the body, not the unsprung mass, so $I_v$ is a speed-normalised response measure, not a validated roughness class.

\subsection{Dual-IMU fusion}
\label{sec:imu-fusion}

The two sensors are the same part, configuration and calibration, so they are combined with equal weights: for RMS, $\sigma$, peak-to-peak, jerk and $I_v$, $x_f = (x_1 + x_2)/2$. Crest factor and the threshold count stay per sensor. Because the sensors are at different points on the vehicle, averaging would hide real differences, so each fused window also reports
\begin{equation}
D = \frac{\lvert \sigma_1 - \sigma_2 \rvert}{\max(\sigma_f,\ \sigma_{\mathrm{floor}})}, \qquad \sigma_{\mathrm{floor}} = 0.05\,\mathrm{m/s^2},
\label{eq:disagreement}
\end{equation}
which approaches 2 when one sensor sees much more than the other. A pair is fused only if the two windows ended within half a window of each other; if one sensor produces nothing for 3\,s, the output falls back to the other and says so. A boot self-test checks the averaging, $D$, the rule that $I_v$ needs both sensors, rejection of a misaligned pair and the fallback. The equal-noise assumption has not been tested on the vehicle.

\section{Battery-management interface}
\label{sec:bms-interface}

This section serves R5 and RQ3. The pack reports voltage, current, state of charge, capacity, temperatures and protection faults over Bluetooth Low Energy in the JBD protocol. An inherited implementation leaked a client object on every reconnection, reconnected on a fixed timer and framed messages by a terminator byte that can occur inside the data. The interface was rewritten with one reused client, reconnection only on a disconnect callback, framing from the declared length field, a checksum, and a plausibility check against a 72\,V pack. It searches every discovered service for the required characteristics instead of assuming the service, and logs every advertiser seen so that a wrong address is visible. The field offsets were confirmed byte for byte against an independently written parser in a teammate's code.

Current status (11 October 2026). Valid frames have been received on the vehicle (74.78\,V, 0.00\,A, 60\%), but the link is intermittent (Section~\ref{sec:inv-bms}). The reading has not been compared with a meter or the pack's app. The pack advertises as \texttt{DB24SA01L24S150ABU}, a 24-cell, 150\,A designation, and inherited documentation describes the traction pack as lead-acid without a BMS, which suggested a separate auxiliary pack. On the road session of 19 October, however, this pack supplied up to 46.9\,A while the vehicle was driven and its voltage fell from 74.6 to 72.8\,V, so it is the traction pack and the documentation is out of date.

\section{Positioning}
\label{sec:gnss-parsing-validation}
\label{sec:gnss-outdoor}

This section serves R4, and RQ1 and RQ3. The modem's GNSS is polled every 3\,s with \texttt{AT+CGNSSINFO}. The parser was written defensively, checking the field count and logging the raw reply, because the manual available \cite{simcoma76xx} was not known to match the fitted modem's firmware. The real reply did differ from the one in the manual (Section~\ref{sec:inv-gnss}). Since v0.5.3 the parser anchors on the latitude hemisphere letter and reads every field relative to it, which fits all observed layouts, and accepts a fix only if the layout and the coordinate, date and time formats are valid and the implied jump from the previous fix is under 100\,m/s; this rejected replies corrupted when a second query competed with the firmware's polling. A console command prints every raw reply so that the parser can be checked without extra commands. Section~\ref{sec:inv-gnss} covers the modem's start-up and GNSS warm-up. The manual gives speed over ground in knots \cite{simcoma76xx}; the unit's readings have still to be checked against a known speed. The reply layouts are in Appendix~\ref{app:devrecord}.

Firmware v0.7.3 adds assisted GNSS, which downloads orbit data over LTE every two hours (\texttt{AT+CAGPS} returned success on the bench), and, while there is no fix, the modem's network position (\texttt{AT+CLBS}) once a minute. Indoors this answered in about 0.7\,s with a reported accuracy of 550\,m, about 30\,m from the first outdoor fix at the same site; it is kept in separate fields, drawn on the map as an approximate circle, and never used for speed, heading or the ride index.

\section{Other vehicle inputs}
\label{sec:environmental-sensing}
\label{sec:hall-tap}

This section serves RQ1 and RQ4; no requirement of Table~\ref{tab:requirements-mapping} depends on it yet. The Sensirion SEN55 reports particulate matter, humidity, temperature and VOC and NOx indices over I\textsuperscript{2}C; the gas indices are relative to recent background and take up to 1 and 6\,h respectively to meet specification after switch-on \cite{sensirionsen5x}, so gas indices from a short drive are indicative only. It was chosen so that conditions along a route can be recorded on the same timeline as the vehicle's measured response. It has been received but is not connected, for want of a six-way JST GH cable; the planned wiring is in Appendix~\ref{app:wiring}.

Motor speed would help separate powertrain vibration (RQ4). The Hall signal is referenced to the drivetrain, so it is to be tapped through a PC817 optocoupler module. Firmware v0.6.0 counts both edges in the hardware pulse counter with a 12.5\,$\mu$s glitch filter, so counting costs the IMU tasks nothing, and computes revolutions per minute as the edge rate divided by twice the pole-pair count, which is not yet known. Until the tap is wired the counter reads the sync pulse as a loopback, against which the count can be checked exactly: on 1 October it counted 666 edges in 333.3\,s, 2.00 edges per second, matching the 500\,ms toggle. Which Hall wire to tap, its voltage (5 or 12\,V) and the optocoupler module's input rating are still to be measured on the vehicle. The same firmware publishes the modem's signal quality every 10\,s so that failed publishes can be related to coverage.

\section{Camera subsystem}
\label{sec:camera-subsystem}

This section serves R6, R7, R8, R10 and R11, and RQ1, RQ2 and RQ3. It covers capture and synchronisation, detection, range sensing and fusion, the dashboard integration, the time-to-contact warning and the two-sided layout.

\subsection{Capture and synchronisation}
\label{sec:sync-pulse}

The camera's first purpose is a visual record against which inertial events can be labelled, for example to tell a pothole from a deliberate manoeuvre. The camera and the inertial data are on different boards, so their clocks are related by a shared signal: a FreeRTOS task on the ESP32 toggles GPIO15 every 500\,ms with \texttt{vTaskDelayUntil} and logs each edge's microsecond time, and the Raspberry Pi~4 logs the arrival of each edge on GPIO17. On the ESP32 side successive logged edges were 500,000 to 500,001\,$\mu$s apart over an extended capture. The first Pi-side logger timestamped edges in a Python callback (\texttt{gpiozero}); its intervals clustered at 500.1 to 500.3\,ms with one unexplained 413.6\,ms gap. The edge logger was therefore rewritten (\texttt{CameraDetection/sync\_logger.py}) to take each edge's time from the kernel through the GPIO character device, on the same monotonic clock as the camera's frame timestamps, which narrowed the spread to under 0.7\,ms (Chapter~\ref{chap:results}); the camera library's \texttt{SensorTimestamp} gives the time at which the first pixel of each frame was read out, on that clock \cite{picamera2manual}. Frames and edges therefore share one time base. Two findings shaped this part. The pin first chosen for the pulse is not brought out on the board, which was caught against the manufacturer's schematic before any wiring. And twice the jumper on the pulse wire was disturbed by handling, once giving no edges and once a 16\,s burst of spurious edges: edges that do not fit the known 500\,ms pattern can be discarded in analysis, but a secured connector is needed on the vehicle. An earlier lens-cover test bounded the offset to under about 1\,s (Appendix~\ref{app:devrecord}). Sub-second alignment is enough for labelling events after the fact.

\subsection{Detection}
\label{sec:hazard-detection}

The detector (\texttt{CameraDetection/hazard\_detector.py}) runs a pretrained SSD-MobileNet-v1 \cite{liu2016ssd, howard2017mobilenets}, trained on COCO \cite{lin2014coco} and quantised to 8-bit integers \cite{jacob2018quantization} for LiteRT \cite{litert}, on 640$\times$480 frames, which needs no training data and no accelerator (Section~\ref{sec:lit-detection}). Only motor vehicles, motorcycles, bicycles, pedestrians and animals are reported, in three distance bands (immediate, warning, monitoring) estimated from the box width, an assumed width per class (for example 1.8\,m for a car) and the pinhole relation. The focal length is not yet calibrated, so the bands are indicative.

An alert is raised when a class appears in a band for three consecutive frames, re-raised if it holds a nearer band for three frames, and cleared only after five frames without it; within a frame the nearest detection of a class is used. The clearing rule came from the second live run, in which an alert that cleared on a single missed frame produced 16 activations in 47\,s for one person. The rules were checked offline by replaying scripted sequences through the unchanged loop, and later seen raising and clearing person alerts on live frames.

Data handling is minimal by design, and was fixed in code before the detector first processed live frames on 28 September 2026. Each alert records five fields: class, band, confidence, timestamp and alert status. Frames exist only in memory and are never written to disk; there is no face or number-plate recognition and no identification of anyone; inference is local; and the output is advisory, with no control of any vehicle function. The ride characterisation of Section~\ref{sec:ride-characterisation} uses no learned model.

Every frame's latency is measured from its \texttt{SensorTimestamp}: the time from readout to capture by the detector, preprocessing, inference, alert logic and the total, reported as median, 95th percentile and maximum every 5\,s and optionally written per frame. The measurement excludes the exposure time itself. Inference uses all four cores. The optional live view draws the detections on the image and serves it as MJPEG from its own thread, which always takes the newest frame, so a slow viewer cannot slow detection. Two input faults were found on the first live run: a placeholder entry in the label file shifted every class by one, and the camera's buffers are in blue, green, red order while the model expects red, green, blue \cite{picamera2manual}. The module's lack of an infrared-cut filter gave a pink cast, corrected by its own tuning file and a saturation of 1.8 (Section~\ref{sec:inv-colour}).

Because the COCO classes include no road-surface hazards, a YOLO11n pothole model \cite{ultralytics2024yolo11} was fine-tuned in Colab, first on a public dataset \cite{gerapothole} and then on tiles cut from the road band of a South African dashcam dataset collected by Nienaber et al.\ at Stellenbosch University \cite{nienaber2015dataset}; the data preparation is in Appendix~\ref{app:devrecord}. On the Raspberry Pi~4 it runs with the NCNN library \cite{ncnn} as an experimental path, off by default, because only at one run every 4\,s did the detector stay within 10\% of its rate without it (13.9 against 14.6\,frames/s; test C10). \outstanding{held-out test score of the pothole model, and a run on a road.}

\subsection{Range sensing and fusion}
\label{sec:tof-sensor}
\label{sec:camera-tof-fusion}

A VL53L5CX was chosen for proximity sensing because its 8$\times$8 zones in a 63\textdegree\ field separate left, centre and right from one device, where single-point sensors would have to be duplicated across directions. It involves no image and no learned model, so it works whatever the detector's state. It had not arrived by 30 September, so the three VL53L0X sensors of a UCT micromouse sensor board stand in, facing left, ahead and right, with a range of about 2\,m (1.2\,m used). They share one address, so the reader holds all three in shutdown and wakes each in turn to give it its own address (Appendix~\ref{app:wiring}). Each camera unit has its own board of three beside its camera on a free bus, on the Raspberry Pi~4 at the rear and, since 15 October, on the Raspberry Pi~5 at the front (Section~\ref{sec:two-sided}), which leaves the ESP32's acquisition undisturbed.

A sensor that does not answer within 0.5\,s is skipped, logged and looked for again every 60\,s (Section~\ref{sec:inv-tof}).

The camera says what an object is and in which direction, but its distance is uncalibrated; each time-of-flight sensor measures distance well, but only close by, in one direction and without a class. A fusion step on each camera unit (\texttt{CameraDetection/sensor\_fusion.py}) combines them. The detector serves each detection with a bearing computed from the box centre and the 53.5\textdegree\ horizontal field, and the bridge polls it five times a second. A detection is matched to a sensor when its bearing lies in that sensor's cone widened by a 5\textdegree\ gate and the sensor's nearest sample is within 200\,ms, valid and in range; the nearest reading wins and each sensor serves one detection. A matched detection becomes a fused hazard with the camera's class and the sensor's distance; an unmatched one keeps the camera estimate; a sensor with three valid in-range readings and no match reports an unclassified obstacle; and camera data older than 1\,s are ignored, so with the detector stopped only obstacles are reported. Hazards are sorted nearest first. The sensor directions were first set to $-35$, 0 and $+35$\textdegree\ (12.5\textdegree\ half-angle) as defaults, not measurements; since 15 October the side sensors are set to $\pm 90$\textdegree, the way they point on both boards (Section~\ref{sec:two-sided}). With the first defaults the side cones ($-47.5$ to $-22.5$\textdegree\ and 22.5 to 47.5\textdegree) overlap the camera's $\pm 26.75$\textdegree\ view only at its outer edges (Figure~\ref{fig:fusion-geometry}), so most objects to the side can be reported only by a time-of-flight sensor, without a class. A sensor reports the nearest surface in its cone, which need not be the object the camera saw, and there is no tracking. A continuous record of distances and bearings would collect more than the system needs, so the fusion log is off by default and is switched on only for a validation session, and then holds numbers only, no images. The bench validation (test C9) first calibrates the camera axis, field of view and each sensor's cone with a narrow target on a marked floor, then checks a person crossing at 1\,m, a person standing at 0.5, 1.0 and 1.5\,m against a tape, a box outside the detector's classes at 0.8\,m (to be reported as a time-of-flight obstacle) and a person at 2.5\,m, beyond the sensors' range (camera only).

\subsection{Dashboard integration}
\label{sec:dashboard-page}
\label{sec:dashboard-link}
\label{sec:live-only}
\label{sec:pi5-default}

An inspection of the inherited PySide6 dashboard on 2 October found no live input: every page ran on simulated data, with one unused entry point for a live vehicle state and a fallback to simulation after 2.5\,s without one. A driver's display should not depend on coverage or a remote broker, so a local path was built. Firmware v0.7.0 prints one compact JSON line a second on USB; a bridge on the Raspberry Pi~4 (\texttt{telemetry\_bridge.py}) reads it with the time-of-flight distances and the fused hazards and serves them over HTTP; and a live-data provider on the Raspberry Pi~5 polls the bridge every 0.5\,s. The dashboard therefore needed one network link for camera, alerts and telemetry. Until 15 October that link was a laptop or phone hotspot (Appendix~\ref{app:wiring}), so the display depended on it. Since then the front camera and its alerts run on the Raspberry Pi~5 itself, and the rear unit and the telemetry are reached over a dedicated Ethernet cable (Section~\ref{sec:two-sided}), so the display no longer depends on Wi-Fi. It finds the Raspberry Pi~4 on any network from a beacon that the bridge broadcasts every 2\,s, with localhost, an override, a wired address, mDNS and the last good address as alternatives (Figure~\ref{fig:pi4-discovery}, Appendix~\ref{app:devrecord}). The design addresses the dashboard issues of Section~\ref{sec:lit-display} as follows; the later redesign of the pages themselves is in Appendix~\ref{app:interface}.

Data validity and update age. A live-only mode (\texttt{TUKZIE\_LIVE\_ONLY=1}) stops the simulation entirely. When the bridge cannot be reached, or the telemetry unit's record is more than 3\,s old, the provider stops sending, and within 2.5\,s the dashboard shows an explicit no-data state: every sensor field empty, every validity flag false, ``-{}-'' or ``Unavailable'' on the pages, and a message that live data was lost. A field with no live source (speed, until the GNSS units are confirmed; pedals; temperatures) stays empty rather than taking a default, and the state of charge stays empty until the BMS reports. This mode was added after two findings: when the Raspberry Pi~4 changed network, the dashboard fell back to simulated values with no sign, and a battery level of 82\% was shown that was the simulator's last value, not a measurement.

Layout. The changes add few elements: a camera page with the live view and the active alerts; a Sensors page with the three distances as gauges, the fused hazards nearest first, and the battery, position, motor and ride readings; a ride-quality card on the diagnostics page; and the driving page's front-obstacle distance, taken from the forward sensor only (since 15 October the ahead sensor of the Raspberry Pi~5's board) so that a car parked alongside does not raise a front warning.

Contrast and colour. Alerts and gauges use the dashboard's own status colours (amber under 1.0\,m, red under 0.5\,m), so the team's visual language is kept. Contrast in daylight has not been measured.

Alert priority. An immediate hazard from the fusion, or loss of the Raspberry Pi~4 link for 5\,s after it was working, raises a banner over every page; touching it opens the Sensors page, and a button hides it for 30\,s. Lower bands appear only on the camera and Sensors pages.

Interaction. Finger-drag scrolling was added and developer options were moved behind one switch. Touch response was reported as slow, so the touch controller was read directly during 25 taps (Chapter~\ref{chap:results}).

The integration is applied as a patch set of 63 edits to a separate copy of the team's dashboard by a deploy script that refuses to touch the team's folder and writes nothing unless every edit's anchor text occurs exactly once, so the team's code is never changed. Since 6 October a system service starts the integrated copy at boot on the Raspberry Pi~5 in place of the team's service, which one command restores. The camera page uses only Qt's networking and widget modules, because the dashboard's web-engine map crashed the program on the Raspberry Pi~5; a street-tile map drawn directly with Qt from OpenStreetMap tiles \cite{osm}, with routes from OSRM \cite{luxen2011osrm}, replaces it. The map and navigation work is summarised in Appendix~\ref{app:devrecord}.

\subsection{Approaching objects: time to contact}
\label{sec:ttc}

A fixed distance band says how near an object is, not whether it is coming closer. On 15 October the detector gained a warning for objects closing on the vehicle, front or rear (\texttt{CameraDetection/hazard\_detector.py}, tests in \texttt{tests/test\_approach.py}).

\begin{itemize}
\item \emph{Tracking.} A small tracker matches detections from frame to frame by box overlap, so each object keeps an identifier through up to two missed frames. Car, truck and bus may continue each other's tracks, because the model swaps them between frames. The identifiers start from 1 at each start-up and identify no one.
\item \emph{Time to contact from scale.} For an object closing at constant speed, its image width $w$ grows so that $1/w$ falls linearly in time, reaching zero at contact. The time to contact is $\tau = w / \dot{w}$, the expansion measure of Section~\ref{sec:lit-detection} \cite{lee1976tau,dagan2004fcw}, and needs no focal length or real object size. It is fitted robustly (a Theil-Sen line \cite{sen1968} through $1/w$ against the frames' sensor timestamps) over the last 0.6\,s. It is used only with at least 5 frames over 0.25\,s, 75\,\% of the pairwise slopes agreeing, at least 5\,\% growth, no box touching the image's side edges, and the height giving a time within a factor of 2.
\item \emph{Alert.} An object is ``approaching'' when $\tau$ is under 4\,s (warning) or under 2\,s (immediate), after the same three-frame onset as the other alerts, and is released above 5\,s (2.5\,s for immediate) or after five frames without a valid estimate. A closing speed from the distance estimate is also reported, but it depends on the uncalibrated focal length.
\item \emph{Close range.} The bridge computes each time-of-flight sensor's closing speed and time to contact over 0.3\,s of readings. Where camera and time-of-flight agree on bearing, the fused hazard takes its time to contact from the sensor inside the sensor's range and from the camera beyond it, and says which.
\end{itemize}

The vehicle's own motion makes a stationary object ahead ``approach'', which is intended: it is then a forward-collision warning. Each warning is logged with its time to contact, track and side. The added work costs about 0.3\,ms per frame on a laptop. The accuracy test (C11: a person walking towards each camera at a measured pace between tape marks, and a car approaching the parked trike in a closed area) has not been run.

\subsection{Two-sided layout}
\label{sec:two-sided}

On 15 October the hardware was rearranged after two findings: the battery-management unit's Bluetooth link did not reach the telemetry unit at the front of the vehicle, and the Raspberry Pi~5 ran the detector more than twice as fast as the Raspberry Pi~4 (Results, Table~\ref{tab:res-camera}). Figure~\ref{fig:two-sided} shows the result.

\begin{itemize}
\item \emph{Front, Raspberry Pi~5} (behind the dashboard): its own OV5647 camera, the detector, a second time-of-flight board and its fusion, beside the dashboard. A front alert no longer crosses the network before it reaches the screen.
\item \emph{Rear, Raspberry Pi~4} (beside the battery): its camera and time-of-flight board now look backwards, and it keeps the telemetry unit on USB. Near the pack the battery-management link connected for the first time (Results, R5).
\item \emph{Link.} A dedicated Ethernet cable joins the two (fixed addresses 10.20.0.1 and 10.20.0.2, no gateway), so Wi-Fi keeps the route to the internet. It ran at 1000\,Mb/s with a 0.22\,ms round trip, and the dashboard found the rear unit over it unaided.
\item \emph{Dashboard.} The Surroundings page gained a Front | Rear switch. A side moves the live picture, the alert list, the three distances and the fused hazards together, each from that side's own unit. The rear picture is mirrored, like a car's reversing camera, with left and right swapped to match. The banner shows warnings from both sides, labelled ``Front'' or ``Rear'', and opens the side it names; selecting reverse on the dashboard's own gear control selects the rear (the vehicle provides no gear signal). Appendix~\ref{app:interface} shows the pages.
\end{itemize}

The side time-of-flight sensors on both boards point straight out sideways, so the fusion's sensor bearings were set to $\pm 90^\circ$; at the earlier $\pm 35^\circ$, a camera detection near the image edge could be paired with a side sensor pointing elsewhere.

\section{Communications and local logging}
\label{sec:mqtt-networking}

This section serves R9 and R10, and RQ3. Every 10\,s the modem task publishes a compact JSON summary of the ride, BMS and GNSS state over MQTT using the modem's own \texttt{AT+CMQTT} commands. Publishing is kept inside the modem task because the modem UART has no lock, and a second task issuing commands would corrupt both streams. The broker is a public, unauthenticated test broker (\texttt{test.mosquitto.org}), used only to prove the path and not as a destination for real vehicle data; the credentials of the vacation-work team's own broker were deliberately not copied into this project's code. For the start, connect and publish commands the modem returns \texttt{OK} and then a separate result line whose code gives success or failure \cite{simcoma76xx}; since v0.5.0 the firmware waits for that line rather than trusting the \texttt{OK}. A session is treated as lost after three failed publishes or when the modem reports a dropped client or lost network; the old session is then shut down in the order the manual requires, and retries start at 30\,s and double to at most 5 minutes. Since v0.5.3 the firmware also reconnects as soon as the modem reports that packet data is available again.

\label{sec:local-logging}
Each record is also written to a LittleFS file system in the 3.5\,MB data partition of the internal flash (Table~\ref{tab:config}), whether or not MQTT is connected, so that a session leaves a complete record without coverage. Two findings shaped this part.

Finding: flash writes pause acquisition. With a write every 10\,s, both IMUs showed a 33 to 40\,ms gap at each write, although they are on separate buses; switching logging off for 120\,s, with publishing continuing, removed the gaps. Writing to flash suspends code executing from flash on both cores, which explains why both stalled together. Since v0.6.0 records are buffered in memory (8\,KB) and written in one append about once a minute. This reduces how often the pause occurs, not its length, and up to a minute of records is lost if power is cut before a flush.

Finding: missing values made invalid JSON, which only reading the whole log back revealed; since v0.6.3 they are written as \texttt{null} (Section~\ref{sec:inv-json}).

The log is capped at 3\,MB and then truncated rather than rotated. The file survives reprogramming and grew by about 160\,KB an hour on the bench, so it must be read back and cleared before a long session such as the road test; after the read-back of 1 October the copy was saved in the repository and the board's file cleared.

\label{sec:db-sync}
Store-and-forward to a central database (v0.7.4). Every record carries a boot counter, a sequence number that never repeats across reboots and, once the GNSS has a fix, the device's UTC time, and is published at QoS~1. A ledger in the modem task tracks the highest sequence number up to which every record has been acknowledged or counted as lost; after a reconnection the task republishes the unacknowledged records from the log, marked as replays, at up to about three a second. On the Raspberry Pi~5 an ingest program (\texttt{Server/sw7\_ingest.py}) stores each record in SQLite once per device, boot and sequence number, and can backfill from a copy of the log; \texttt{Server/sync\_report.py} reports missing and duplicate records, replays, drain time and, with device UTC, latency. The ledger passed 900 randomised outage and reboot simulations on the laptop before test T15.

\section{Fault investigations}
\label{sec:investigations}

This section serves R1, R4, R5, R8, R9 and R10, whose tests exposed the faults below, and RQ3. Most faults in Table~\ref{tab:faults} were fixed in one step; the seven below needed a diagnosis, because more than one cause could explain what was seen. Each is told as symptom, candidate causes, deciding test, cause and fix, and consequence, and Table~\ref{tab:investigations} summarises them.

\subsection{Boot loop after enabling the full flash}
\label{sec:inv-flash}

\emph{Symptom.} The build tool treated the board as an 8\,MB part without PSRAM, although the module has 16\,MB of flash and 8\,MB of PSRAM. Setting the flash size to 16\,MB with a matching partition table made the processor reset about once a second, always at the same program counter.

\emph{Candidate causes and tests.} The PSRAM setting, the flash override, the code or the hardware. One setting was changed at a time. Adding a PSRAM type (\texttt{qio\_opi}) left the same loop at the same program counter, so PSRAM was not the cause on its own. Removing every override restored normal running, which cleared the code and the hardware. Two independent readings then pointed to the flash access mode: the upload tool's chip detection confirmed 8\,MB of PSRAM, and the ROM boot banner reported the flash in dual-I/O (DIO) mode, while the setting tried asked for quad-I/O.

\emph{Fix and consequence.} The firmware used about 9\% of the default partition, so the stock configuration was kept until local logging needed the 16\,MB table. Then 16\,MB with DIO mode, set together with the table, booted and mounted the logging partition, confirming the diagnosis. Size, mode and table must be set together.

\subsection{Modem power key, GNSS warm-up and reply layout}
\label{sec:inv-gnss}

\emph{Symptoms.} Three problems overlapped. Indoors every GNSS poll had the wrong number of fields; for 60 to 90\,s after the GNSS was switched on, polls got no reply; on a rooftop the first fix was reported near latitude and longitude zero (0.25 and 0.10 degrees); and a later five-minute capture got no reply to any of its 69 polls.

\emph{Candidate causes and tests.} A reply layout other than the 13 fields assumed, a normal receiver start-up delay, or a modem that was not running. Because the parser logged the raw reply, the real layout was visible: nine empty fields indoors and, with a fix, 17 fields (18 while settling) in decimal degrees, so the old mapping had read satellite counts as the position. A modem that had run for several minutes answered every poll, and during warm-up it answered other commands at once, so only the GNSS was waiting. The silent capture did not fit warm-up, as MQTT commands also went unanswered: the power key toggles the modem, which keeps its supply when only the processor restarts, so the pulse sent at every boot switched a running modem off after each reprogramming.

\emph{Fixes and consequence.} Since v0.5.3 the parser anchors on the latitude hemisphere letter (Section~\ref{sec:gnss-parsing-validation}); since v0.5.2 the key is pulsed only if the modem does not answer \texttt{AT}. Tests must allow the warm-up, during which a zero poll count does not mean that polling has stopped.

\subsection{Battery-management connection and checksum}
\label{sec:inv-bms}

\emph{Symptoms.} In turn: no BLE advertisements from any device; once the pack was powered, a link that dropped before any data; mostly failed connections; and on the vehicle three frames, all rejected on the checksum.

\emph{Tests and causes.} Every advertiser was logged, so seeing no device at all in a room full of them showed that the scanner was idle: scanning depended on an address set only after the pack had been found. A teammate's independently written parser finds the characteristics directly, which showed that in the ESP32 library they are not under the assumed service; every service is now searched. A power cycle of the board did not change the failed connections, which ruled out a stuck BLE stack. The checksum formula came from community reverse engineering. The query frame the firmware itself sends, \texttt{DD A5 03 00 FF FD 77}, carries $\mathtt{0x10000} - (\mathtt{0x03} + \mathtt{0x00}) = \mathtt{0xFFFD}$, which leaves out the byte in the register position; the firmware included it, so every genuine reply failed by exactly three.

\emph{Fix and consequence.} Firmware v0.5.4 corrects the sum and prints the bytes of any frame that still fails; 14 consecutive valid records followed on the vehicle. The protocol is confirmed, but the signal on the vehicle, $-88$ to $-93$\,dBm, is near the limit for a link, so the unit may have to be mounted near the pack.

\subsection{Invalid JSON found only by reading the log back}
\label{sec:inv-json}

\emph{Symptom.} At the first read-back of the stored log, on 1 October, 5,545 of 6,020 records failed to parse as JSON. Earlier transfer attempts had lost characters.

\emph{Candidate causes and test.} Damage in transfer, over a serial link that also carries other output, or records wrong as stored. The dump command prints each record with its index and length, and the laptop script (\texttt{BenchTest/log\_dump.py}) discards any record whose length does not match and repeats until every index has arrived intact. After four passes all 6,020 records were intact, so transfer was ruled out. Every failing record contained \texttt{nan}: a field with no value, such as the position before a fix, was printed as \texttt{nan}, which JSON does not allow.

\emph{Fix and consequence.} The same text had been published over MQTT, and watching the live output had not shown it. Since v0.6.3 such fields are written as \texttt{null}, and all 6,020 records parse. A strict receiver would have rejected 92\% of the records; later link tests count the lines that fail to parse at the receiving end (Appendix~\ref{app:evidence}).

\subsection{Camera colour cast}
\label{sec:inv-colour}

\emph{Symptom and candidate causes.} The live view looked reddish. A test was written for each of three causes: the detector's channel order, the camera itself, and the module's lack of an infrared-cut filter, which has its own tuning file.

\emph{Tests and cause.} A still with the standard tuning showed a white wall strongly pink, as did the detector's frames; with the tuning for a module without the filter the wall was neutral. The cause was the module, not the channel order.

\emph{Fix and consequence.} That tuning alone washed the colours out (a blue card at 120, 124 and 125 on red, green and blue); a saturation of 1.8 restored them (Table~\ref{tab:colour-cards}). Black objects then looked purple, since many black materials reflect infrared; greying near-black pixels took 84 to 171\,ms a frame, too slow for the detection loop, so it is done in the live view only. The colours must be checked again in daylight, where there is more infrared. Whether the cast lowered detection confidence was not measured.

\subsection{Time-of-flight start-up hang}
\label{sec:inv-tof}

\emph{Symptoms.} On 6 October every distance from the three sensors was null; after a first fix, on 10 October the reader froze.

\emph{Tests and causes.} A scan of the I\textsuperscript{2}C bus showed only the left sensor, at its new address, and nothing when the ahead sensor was woken. One sensor was not answering, but the start-up, which gives each sensor its address in turn, stopped at the first failure and lost all three. The reader was changed to skip and log such a sensor, and the bridge to look for it again every 60\,s. That relies on an error being raised, and on 10 October none was: the driver's I/O timeout defaults to zero, which means wait for ever, so one stuck sensor froze all three.

\emph{Fix and result.} Each sensor now has a 0.5\,s I/O timeout. With it, the reader no longer froze but logged all three sensors as timing out, while a device stayed at the shared start-up address 0x29 throughout, even with every shutdown line held low: one sensor was not under the control of its shutdown line. After the sensor board's wiring was re-seated, all three opened, and in a three-minute hand test the ahead and right sensors read 80 to 264 and 157 to 199\,mm with a hand about 20\,cm away (\texttt{BenchTest/logs/2026-10-10\_tof\_hand\_test.txt}).

\emph{Consequence.} The loose wire was inferred from these symptoms, not seen. If a shutdown (XSHUT) wire comes off, its pull-up keeps that sensor on at the shared start-up address, where it collides with each sensor being woken, and none of the three starts (Appendix~\ref{app:wiring}). The timeout turns this into a logged failure, visible before a test, but cannot keep the other two running.

\subsection{Raspberry Pi~4 under-voltage and reboots}
\label{sec:inv-power}

\emph{Symptoms.} Through much of the bench work the Raspberry Pi~4 reported under-voltage and throttled to 600\,MHz. On 4 October the detector ran at 6.1\,frames/s, against 14.6 later on a healthy Pi with the same services (\texttt{BenchTest/logs/2026-10-10\_bench\_observations.md}). On 6 October the Pi stopped booting until everything was disconnected.

\emph{Candidate causes.} The Pi's own supply under the detector's load; the time-of-flight board on its I\textsuperscript{2}C bus; the telemetry unit on its USB port; or heat, since it had no cooling.

\emph{Test.} A logger recorded every 2\,s the power and temperature flags, the I\textsuperscript{2}C addresses and the USB serial devices, so that each change in the flags could be matched to a device (\texttt{BenchTest/logs/2026-10-06\_pi4\_power\_watch.log}). With nothing attached and the detector running, the flags were clear, which cleared the supply. The time-of-flight board stayed disconnected. From 17:45 the soft temperature limit came and went (65 to 69\,\textdegree C) with no under-voltage. The telemetry unit was plugged in at 17:58:05; 14\,s later, when its modem came up, under-voltage and throttling began and recurred every few seconds, and the detector slowed from 14.3 to 12\,frames/s.

\emph{Cause.} The modem's transmit current, drawn through the Pi's USB port, pulls the Pi's supply down; the current was not measured. On 10 October, with the unit on the Pi's USB port, the Pi restarted three times in about 20 minutes; after the unit was moved to the laptop (through a small hub without its own supply), there were none in 4 hours and the flags stayed clear. The boot failure of 6 October was probably the same fault but was not reproduced. Heat was separate: 81\,\textdegree C without cooling, 48 to 66\,\textdegree C with a fan.

\emph{Fix and consequence.} The fault lay in how the parts were powered together, not in any one part. The telemetry unit needs its own supply, such as a powered hub, on the bench and on the vehicle. On a 3\,A supply the Raspberry Pi~5 limits its USB ports to 600\,mA in total (its supply on the vehicle is still to be confirmed), so the same applies there, and a measured power budget against the 72\,V source is still needed.

\emph{Recurrence in the closed housing (16 October).} With the Raspberry Pi~4 in the printed box, still powering the telemetry unit from its USB port, its temperature rose from 68.6 to 73.5 and then 76.9\,\textdegree C over about 70 minutes with the detector running. The flags showed under-voltage, throttling and the soft temperature limit since boot (0xD0000). Later the same day it restarted while under-voltage was present at that moment (0x50005): a brown-out. In the same period the share of unreadable dashboard lines rose from about 2 to 10\,\% once the battery-management link became active. Two changes followed. The box had vents only in its floor and low in one wall, so both pods' lids gained an exhaust grille over the computer under a push-on rain hood (Appendix~\ref{app:mechanical}); and the telemetry unit must have its own supply, as found above. The temperature in the vented box and the line-loss figure with a separate supply have not yet been measured. The Raspberry Pi~5 also restarted four times during the mounting work on 19 October. A power logger recording its supply, flags and temperature every 5\,s showed normal values in the last reading before each restart (4.95 to 5.08\,V, flags clean, 57 to 59\,\textdegree C). The supply's lowest reading in the two minutes before each was 4.89 to 4.97\,V. Those were abrupt losses of power, from a loose connector, the source or the supply's overload protection, not a brown-out or overheating.

\emph{Separate supply and a wired serial link (21 October).} During the road session the telemetry unit was still powered from the Raspberry Pi~4's USB port, which also carried its data. It was then given its own battery, and the Raspberry Pi~4 started with no under-voltage messages, against 11 to 16 per start before. USB could no longer be used for data, because the board charges its battery from that port and would load the Pi again. The data moved to three wires instead: the unit's spare pins IO41 and IO42 to the Pi's UART on header pins 10 and 8, and a common ground, with no supply wire between them. Firmware v0.7.4.1 sends every dashboard line on this link at 460\,800\,baud, drops and counts a line rather than wait if the link's buffer is full, and accepts the local commands from the Pi. On the Pi, Bluetooth, which nothing uses, was disabled so that the full UART rather than the clock-dependent mini UART is on those pins, and the serial console was removed from them. In the first check the bridge read 216 lines without a bad one, and 2,489 by midday, against 2 to 11\,\% lost on USB and a third of the per-second records missing on the road session (Section~\ref{sec:res-acq}); 27 records from that session also had damaged fields. Running on its own battery, however, the unit restarted by itself, after which its modem did not answer for the rest of the morning, which fits the battery sagging under the modem's transmit bursts. A battery alone is therefore not the answer: the unit needs a regulated supply from the vehicle.

\section{Testing infrastructure}
\label{sec:bench-tools}

This section serves the tests of every requirement, R1 to R13, and so all four research questions: it describes the tools that produce the records of Section~\ref{sec:data-collection}. Tools were written so that each test leaves a record that can be checked later. A browser dashboard reads the telemetry unit's serial output over USB through the Web Serial interface, with no installation, and shows the fused and per-sensor ride features, each IMU's rate and drop count, GNSS and BMS status, free memory and the boot self-tests, with rolling plots of vibration and disagreement (Figure~\ref{fig:live-dashboard}, Appendix~\ref{app:figures}). It can replay a saved log through the same parsing, so a recorded session is reviewed exactly as it appeared live. The subsystem pages were later combined into one bench console that also shows the camera's live view and alerts, sends the firmware's console commands, filters the log by subsystem and saves timestamped sessions; it only reads data, and was checked by replaying the recorded session (Figure~\ref{fig:console-replay}, Appendix~\ref{app:evidence}). Scripted tests drive the firmware and record the result: \texttt{BenchTest/v050\_bench\_test.py} (commands, logging and reconnection), \texttt{BenchTest/signal\_loss\_test.py} (radio off for 60\,s), \texttt{BenchTest/sync\_outage\_test.py} (radio off for 10 minutes, then backlog drain), \texttt{BenchTest/log\_dump.py} (full log read-back) and \texttt{BenchTest/sw7\_check.py} (pre-test check of every link). Offline tests replace the camera, model or bridge with stand-ins so that the detector's alert rules, the fusion and the dashboard pages can be checked without hardware.

\section{Maintenance design}
\label{sec:maintenance}

This section serves R13 (a removable installation) and the maintainability expected of a prototype that others in the programme will keep running; it supports RQ3, since recovery depends on how faults are found and fixed. The provisions below were checked in the repository; what is not yet maintainable is listed at the end.

\begin{itemize}
\item \emph{Firmware updates.} The telemetry unit's firmware is a PlatformIO project (\texttt{TelemetryUnit/\allowbreak platformio.ini}, \texttt{TelemetryUnit/\allowbreak src/main.cpp}). It is built and flashed over the board's native USB port with \texttt{pio run -t upload}, and the board settings that caused the boot loop (16\,MB flash, DIO mode, the 16\,MB partition table) are fixed in that file with the reasons beside them (Section~\ref{sec:inv-flash}). The libraries are declared there with minimum versions, not pinned, so the installed versions are recorded separately (Table~\ref{tab:config}).
\item \emph{Version strings.} One constant in \texttt{main.cpp} holds the firmware version (v0.7.4.1 at the time of writing). It is printed in the boot banner and by the \texttt{!status} command, and carried in the \texttt{fw} field of every published record and dashboard line, so each stored record says which firmware produced it.
\item \emph{Calibration and logs from the console.} The calibration factors are kept in non-volatile storage across reprogramming, and the console has commands to recalibrate, to switch local logging off and on, to flush it, and to dump and clear the stored log (Sections~\ref{sec:imu-magnitude-calibration} and~\ref{sec:local-logging}).
\item \emph{Deployment from the repository.} The Raspberry Pis are set up from files in the repository, not by hand. \texttt{CameraDetection/\allowbreak deploy/} holds the services for the rear unit's detector and telemetry bridge and an installation guide (\texttt{INSTALL.md}). \texttt{DashboardIntegration/\allowbreak deploy/} holds the dashboard's deploy script, the patch tool, the start script, the link set-up script for the Ethernet cable and the services for the dashboard, the front detector, the front time-of-flight bridge and the road recorder. The deploy script copies the integration to the Raspberry Pi~5, keeps the previous copy as \texttt{\textasciitilde/Dashboard\_sw7.prev}, rebuilds the copy from the team's dashboard, applies the patches and writes the deployed git commit to a \texttt{DEPLOYED\_COMMIT} file, so the version running on the vehicle can be traced to the repository (Section~\ref{sec:dashboard-page}). The team's own dashboard is never changed, and one command restores its service.
\item \emph{Services that restart.} The detectors, the bridges, the dashboard and the road recorder run as systemd services that start at boot. The detectors, the bridges and the dashboard restart on failure after 3 to 5\,s, and the road recorder restarts always. A crash therefore costs seconds of data, not the session, and the service logs keep the cause.
\item \emph{Tests that travel with the code.} The camera programs have tests in \texttt{CameraDetection/\allowbreak tests/} (alert logic, sensor fusion, time to contact, telemetry bridge, latency and others), the dashboard integration in \texttt{DashboardIntegration/\allowbreak tests/}, and the store-and-forward ledger a host test (\texttt{TelemetryUnit/\allowbreak test\_host/}); a change can be checked against them before it is deployed. The pre-test check (\texttt{BenchTest/\allowbreak sw7\_check.py}) reports every link before a session.
\item \emph{Hardware access.} The display and the sensor pod come off the vehicle without tools, on a bar clamp with a dovetail rail and a locking thumb screw, for charging, security and bench work (Table~\ref{tab:mech-choices}). Repeated joints use heat-set inserts so that they survive being opened many times. The rear pod has a side hatch for the Raspberry Pi~4's flash drive. The revision-3 IMU pods are screwless, with push-fit lids, and the vent hoods push into the lids without screws (Appendix~\ref{app:mechanical}). Every wire is listed by connector and pin in Appendix~\ref{app:wiring}, so a unit can be rewired from the report alone.
\item \emph{Records for diagnosis.} The evidence index (Appendix~\ref{app:evidence}), the lab notebook, the change log and the development record (Appendix~\ref{app:devrecord}) give each fault, its cause and its fix, so a recurring fault can be recognised.
\end{itemize}

Not yet maintainable. The firmware has no over-the-air update: \texttt{main.cpp} contains no update code, so a new version needs a USB cable connected to the unit itself, which sits in the rear pod on the vehicle. The upload port is fixed in \texttt{platformio.ini} (COM10 on the development laptop), so another computer needs that line changed. The stored log must be read back and cleared by hand before it reaches its 3\,MB cap (Section~\ref{sec:local-logging}). The vehicle installation has not been timed for removal and return to standard (R13, Chapter~\ref{chap:results}), and the enclosures have not yet been tested for how often they can be opened.

The design described in this chapter is what the experiments of Chapter~\ref{chap:method} were run on. Chapter~\ref{chap:results} gives their results, requirement by requirement.
